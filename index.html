About the speed

Five times which Rails?

Through Phase 9, every phase was held to a floor of five times Rails, measured with bench/quick against stored numbers for an old, pinned Rails: about 107 room pages a second with one client, 239 with sixteen. Every phase cleared it, which is where the earlier “five times Rails” came from.

Basecamp's harness runs current Rails with a page cache, and it serves 4,944 room pages a second: 21× the pinned one. The first run there put theDotNetWay at 0.68×–1.51× Rails on the reads (1.06×–2.02× with a writer). The room page was slower than Rails'.

Phase 10 found why: about half a millisecond of CPU a page, most of it the data layer opening a pooled connection and preparing a statement for every one of nine statements, and the JIT still warming up on the first route. It opened one connection per request, set the tiering delay to zero, moved one slow read to Dapper, and added a page cache in the four GET actions on HybridCache that re-reads the session and the membership on every hit. The framework's OutputCache could not do it: it never stores a response that sets a cookie, and the room page always does.

Now every route alone is 6.83×–7.83× current Rails, and the new floor is measured on Basecamp's harness, in the same session. Each step, measured →

The climb

Lines down. Speed lost, then found.

From the fork (39.4 KLOC) to 26.5 KLOC, one layer a phase. The data layer's move to EF Core cost the pages most of their speed, Dapper on the hot reads made them about half again as fast, and Phase 10, the page cache, took the room page from 7,215 to 33,418 requests a second on bench/quick.

Layer by layer

What the framework replaced.

It started as a fork of the F# port and swapped one layer a phase, each behind the pixel gate, the cookie round trip and the database differential. Hand-written code stays only where Rails parity needs it: the cookie formats, Loofah's sanitizer rules, Rails' markup quirks.

  3. Between Phase 2 and Phase 3

    Hot reads on Dapper

    In the portEvery per-request read through EF's LINQ pipeline, the room page's nine statements included.

    NowDapper for the per-request read paths only, in one file, parameters only, each read checked against EF's answer over the seed. EF Core keeps every write, every cold query, the model and the schema.

    Why Dapper is still the .NET way. EF Core for the model, the writes and the transactions, a micro-ORM for the hot queries: that split is the read side of the CQRS pattern in Microsoft's own .NET microservices guide, where eShop's ordering service queries with Dapper and writes with EF Core. It was measured first (a spike on its own branch), kept to one file, and every Dapper read is tested against the EF query it replaced. A statement cache or hand-built SQL would have been faster still; neither is the framework's way, so neither is here.
